## 1. Цель

Инженер на новом телефоне входит в Качество 2.0 и через ≈ 10–15 с видит всю историю (сейчас ≈ 40–80 с); вкладки и фильтры аналитики переключаются без заметной паузы (сейчас ≈ 0,5–1 с); приложение не выгружается iPhone при 10 тыс. проверок.

## 2. Подтверждённое исходное состояние

- Новое устройство: `sync-engine.core.js:1043-1044` — `rbiPullRowsByInspectionIds(..., ids, 40)`, пачки по 40 проверок, страница 500 (`sync-core.state.js:361`, `sync-pull.policy.js:36-37`), строго последовательно + пауза 20 мс → 271 запрос на 3000 проверок. Локальные записи сверяются `dbGet` на каждую проверку (замеры).
- База устройства: 11,6 МБ на 3000, из них `checklistSnapshot` 5,3 МБ (46%). Пишется в `audit.actions.js:175,823` (снимок чек-листа на момент проверки — для открытия старых проверок). **Читателей в коде не найдено** (`git grep checklistSnapshot`) — подтвердить на этапе 3, уходит ли он на сервер (`details`, `sync-engine.core.js:2480-2505`): «Не подтверждено».
- Память: вся история целиком в JS, 84 МБ после запуска, 110–115 МБ в аналитике, 11 тыс. DOM-узлов.
- Аналитика: `js/modules/quality/features/analytics/*` (≈ 11,7 тыс. строк); самое долгое подвисание вкладки 63–130 мс на Mac, смена периода 104 мс; свёрнутые блоки рисуются сразу.

## 3. Объём реализации

1. Загрузка нового телефона: пачки 150–200 проверок, до 3 запросов одновременно, одна выборка локальных записей вместо `dbGet` на каждую; прогресс в процентах.
2. Аналитика: свёрнутые блоки («Динамика», «Причины», «Зоны риска», «Фотогалерея») рисуются при раскрытии; смена фильтров/периода — одна перерисовка через 300 мс; «История» — порциями по мере прокрутки; повторные расчёты одной вкладки — из кэша до смены данных/фильтра.
3. Снимок чек-листа — один раз на версию шаблона (отдельное хранилище по хэшу), в проверке — ссылка; старые записи переводятся один раз при запуске (новая версия базы устройства), с откатом при ошибке.
4. «Облегчённая» история в памяти: список и аналитика — без тяжёлых полей (полные `details`, снимок, фото-ссылки, если аналитике не нужны); полная проверка читается из базы при открытии/редактировании/отправке.
5. Стенд на 10 000 проверок (сидер), замеры до/после, документы.

## 3а. Reuse review

- **Найдено:** `pullPagedByIds` (`sync-pull.policy.js`, unit-тесты P2-0023) — EXTEND (параллельность, размер пачки); `storage-photo-loader.js` (ленивость по видимости) — REUSE-подход для порций «Истории»; `dbGetAll`/`dbPutBatch` — REUSE; метрики `getProductMetrics` — REUSE для замеров.
- **Решение:** EXTEND существующих модулей; новых сервисов не создавать, кроме чистой функции «облегчить проверку» с unit-тестами.
- **UI:** вид экранов не меняется; проверить 375 / 1280 px, светлая и тёмная темы, состояния «загрузка» у блоков, раскрываемых по требованию.
- **Совместимость:** все потребители истории (аудит, история, аналитика, ТИВИ/«магия», ИИ-сводки, экспорт PPTX, геймификация, синхронизация) — регрессия на этапе 4.

## 3а. Единый источник истины

- Полная проверка — только в базе устройства (IndexedDB) и на сервере; облегчённая — производная, никогда не записывается обратно и не отправляется.
- Снимок чек-листа — одно хранилище по хэшу; запись проверки хранит хэш.
